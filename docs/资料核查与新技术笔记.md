# 资料核查与新技术笔记

本文件记录开发过程中**真实遇到的技术疑问**、核查途径与结论，用于报告的「新技术认识与适用局限」
「自主学习与资料分析」「持续学习计划」三个评分点。所有结论都来自可复查的一手材料。

---

## 1. 核实方式（我的固定动作）

1. **先看编译器怎么说**：hvigor 编译报错会给出规则编号（如 `arkts-no-untyped-obj-literals`），
   这比搜索引擎更快命中官方规则条目。
2. **再读本机 SDK 声明文件**：`E:\DevEco Studio\sdk\default\openharmony\ets\api\*.d.ts` 与
   `...\ets\component\*.d.ts`，每个接口都带 `@since`、`@syscap`、`@kit` 注释，版本信息最可信。
3. **最后对照官方文档**：华为开发者文档站（`https://developer.huawei.com/consumer/cn/doc/`）
   的「ArkTS 语言」「ArkUI 状态管理」「ArkData（Preferences / 关系型数据库）」章节，用标题检索。
4. **自己动手复现**：写最小工程验证（本项目就是先跑通最小 HAP 编译与 `node --test` 再铺开）。

## 2. 疑问一：为什么 ArkTS 禁止 `Object.assign` 与「无类型对象字面量」？

**现象**：写测试辅助函数时用 `Object.assign(base, overrides)` 造规则对象，
编译直接失败：`Usage of standard library is restricted (arkts-limited-stdlib)`；
另一边 `Select(METRIC_META.map(m => ({ value: m.label })))` 报
`Object literal must correspond to some explicitly declared class or interface (arkts-no-untyped-obj-literals)`。

**查证**：
- 编译器给出的规则名即为官方 ArkTS 约束条目（`arkts-limited-stdlib`、`arkts-no-untyped-obj-literals`）。
- 本机 SDK `ets/component/common.d.ts` 中 `SelectOption` 是显式声明的接口，
  因此 `map` 回调必须标注返回类型 `SelectOption` 才能通过类型检查。
- 官方文档《ArkTS 语言 · 语法适配规则》说明：ArkTS 在 TypeScript 基础上做了静态化限制，
  以保证 AOT 编译与运行时性能。

**结论与做法**：把 `Object.assign` 换成显式构造函 数（`makeRule(...)` 逐字段赋值）；
把 `.map()` 的回调标注返回类型。这个约束在 Node 侧不存在，因此**领域层刻意只写两边都合法的最小子集**，
同一份 `.ts` 才能既进 App 又进测试。

**局限认识**：这类限制提高了性能与可预测性，代价是 TS 生态里大量动态写法（`Object.assign`、动态属性、
索引访问、`any`）不可用，迁移旧库时摩擦大。

## 3. 疑问二：`@State` 为什么改了嵌套字段界面不刷新？

**现象**：把 `this.snapshot.env.temperature = 30` 之后界面不动。

**查证**：
- 本机 SDK `ets/component/common.d.ts` 中可见 `@State`、`@Prop`、`@Link` 等装饰器声明；
  同时该文件已声明 `ComponentV2`、`Local`、`Param`、`LocalBuilder`（其文档注释处最后一处 `@since 12`），
  说明 API 17 上 V1 与 V2 两套状态管理并存。
- 官方文档《ArkUI 状态管理》指出 V1 的 `@State` 对对象只观察**第一层**赋值，深层字段需要
  `@Observed`/`@ObjectLink` 或整体替换；V2 用 `@ObservedV2` + `@Trace` 做深观察。

**结论与做法**：本项目统一采用**不可变更新 + 整体替换**：`cloneSnapshot()` 生成新快照后赋给
`@State snapshot`，所有子组件通过 `@Prop` 拿数据、通过回调把事件抛回父组件。
好处是不依赖装饰器细节、行为可预测，配合领域层纯函数还能被 Node 测试覆盖。

## 4. 疑问三：Preferences 与 RDB 到底怎么分工？

**查证**（本机 SDK）：
- `ets/api/@ohos.data.preferences.d.ts`：命名空间 `preferences` 标注 `@since 9`（另有 `@since 10` 的
  crossplatform 版本），`@kit ArkData`，`@syscap SystemCapability.DistributedDataManager.Preferences.Core`；
  `getPreferences(context, options)` 这一重载标注 `@since 11`。
- `ets/api/@ohos.data.relationalStore.d.ts`：`@since 9` / `@since 10`，同样属于 `@kit ArkData`。

**结论与做法**：
- **Preferences 适合「整份小配置」**：本项目把 `Snapshot` 序列化成一个 key（`snapshot_v2`）存取，
  一次 `put + flush` 就完成保存，天然带版本号便于迁移。
- **RDB 适合「会不断追加、需要按条件排序查询」的数据**：执行日志用表 `trigger_log` 存，
  带 `fired_at`、`ord` 排序与 `limit` 限制条数，避免 Preferences 里塞无限增长的数组。

**局限认识**：Preferences 是 KV 型、值体积有限，不适合存大量结构化记录；RDB 有建表与版本管理成本，
小配置用它属于过度设计。二者共用必须注意**一致性**（本项目只把日志放 RDB，快照放 Preferences，
避免跨存储事务问题）。

## 5. 一项鸿蒙新技术：状态管理 V2（`@ComponentV2` / `@Local` / `@Param`）

- **用途**：解决 V1 在深层对象、类实例、跨组件共享上的观察盲区，用 `@ObservedV2` + `@Trace`
  做属性级追踪，`@Param` 替代 `@Prop` 做单向输入，`@Local` 替代组件内 `@State`。
- **适用版本**：本机 SDK（HarmonyOS 5.0.5 / API 17）的 `ets/component/common.d.ts` 已声明
  `ComponentV2`、`Local`、`Param`、`LocalBuilder`，其注释区最后一条 `@since` 为 12；即 API 12 起可用，
  在 API 17 上属稳定能力。可用同文件检索 `declare const ComponentV2` 复核。
- **为什么本项目没有采用**：领域层是纯函数 + 不可变快照，V1 的「整体替换」已经能保证刷新正确，
  换 V2 收益不明显；同时 V1/V2 混用有明确限制（同一组件树内混用需要谨慎），
  对单人期末项目来说风险大于收益。这是**基于需求的取舍**，不是能力缺失。
- **局限**：V2 需要改造既有 `@State` 写法，类需要 `@ObservedV2` + `@Trace` 标注，嵌套集合的观察仍有边界；
  老项目迁移成本高，且社区资料多数仍以 V1 为主。

## 6. 关于动画 API 的一点实践

本项目的执行结果浮层用全局 `animateTo({duration, curve}, () => { this.showResult = true })`。
本机 SDK 中该函数仍以 `declare function animateTo(value: AnimateParam, event: () => void): void;` 形式声明
（`ets/component/common.d.ts`，未标注 `@deprecated`），因此编译与运行均可用。
需要留意的局限：全局函数依赖当前 UI 上下文，多窗口/多实例场景下更稳妥的是通过 `UIContext` 取实例方法。
这是我在查 SDK 声明时顺带确认的边界，后续会作为持续学习项跟踪。
