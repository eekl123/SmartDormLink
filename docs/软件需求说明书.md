## 1. 需求与问题分析

### 1.1 背景与用户

高校宿舍里的用电设备越来越多（灯、风扇、加湿器、窗帘），学生常见诉求是：
「热了自动开风扇」「又闷又潮就开除湿」「光线不够补个灯」「太阳太晒把帘子拉上」。
现实中这些设备分属不同 App，条件与动作割裂，规则触发后也没有可复盘记录，出了问题只能靠猜。

本应用面向**宿舍同学（规则定义者 + 使用者）**，把「条件 → 动作」抽象成可编辑规则，
在纯软件的 Mock 环境中即时验证规则效果，并把规则、设备状态与执行记录全部留在本机。

### 1.2 要解决的三个具体问题

1. **规则要能被定义和修改**：不想写代码，用界面就能增删改条件、动作、优先级。
2. **规则要能被验证**：改了环境数据要立刻看到「谁触发了、设备变成什么样、按什么顺序执行」。
3. **冲突要有说法**：两条规则都想控制同一盏灯时，必须能说清谁赢、为什么赢。
4. **结果要留得下**：杀掉进程再打开，规则、设备状态、历史记录都还在。

### 1.3 范围（做什么 / 不做什么）

**做**：规则增删改查与启停、4 类设备状态控制、3 项环境 Mock 数据、规则引擎求值与冲突裁决、
执行日志（含顺序与冲突说明）、2 组场景一键演练、Preferences + RDB 持久化、表单校验、恢复出厂。

**不做**（明确排除，避免范围蔓延）：真实硬件通信、云平台同步、账号体系、AI 生成规则、
多用户协作、时间/日程条件、复杂表达式与跨指标运算、深色模式与横屏适配。

### 1.4 可验收的功能清单

| 编号 | 功能 | 验收判据 |
| --- | --- | --- |
| FR-1 | 环境 Mock | 3 个滑块可调；数值越界被限制在区间内；调整后立即写入界面状态 |
| FR-2 | 设备控制 | 4 台设备可手动开关；开启后档位滑块可用；档位 0-100 |
| FR-3 | 规则列表 | 展示名称、优先级、条件文案、动作文案、冷却、启停开关；可进入编辑、可删除（二次确认） |
| FR-4 | 规则编辑 | 可改名称、且/或、优先级 1-10、冷却 0-600s、条件 1-3 条、动作 1-4 条 |
| FR-5 | 表单校验 | 空名/重名/超长/空条件/空动作/阈值越界/设备不存在/优先级越界/规则超过 12 条时给出具体错误并阻止保存 |

## 2. 数据与状态分析

### 2.1 关键数据

| 数据对象 | 字段（类型） | 说明 |
| --- | --- | --- |
| `DeviceState` | `id: string`、`kind: 'light'\|'fan'\|'humidifier'\|'curtain'`、`name: string`、`room: string`、`power: boolean`、`level: number(0-100)` | 一台可控设备的当前状态 |
| `EnvState` | `temperature: number(-10~50)`、`humidity: number(0~100)`、`illuminance: number(0~2000)` | 一次 Mock 环境采样 |
| `Condition` | `metric: MetricKey`、`op: 'gt'\|'gte'\|'lt'\|'lte'\|'eq'`、`value: number` | 单条触发条件 |
| `DeviceAction` | `deviceId: string`、`power: boolean`、`level: number(0-100)` | 单条设备动作 |
| `Rule` | `id`、`name`、`enabled`、`logic: 'and'\|'or'`、`conditions: Condition[]`、`actions: DeviceAction[]`、`priority(1-10)`、`cooldownSec(0-3600)`、`lastFiredAt`、`updatedAt` | 一条自动化规则 |
| `TriggerLogEntry`（= `LogEntry`） | `id`、`at`、`source`、`order`、`ruleId`、`ruleName`、`priority`、`conditionsText`、`changesText`、`conflictText`、`fired` | 一条执行日志 |
| `ConflictNote` | `deviceId`、`deviceName`、`winnerRuleId/Name`、`loserRuleId/Name`、`reason` | 一次冲突裁决 |
| `Snapshot` | `version`、`savedAt`、`activeScenarioId`、`env`、`devices[]`、`rules[]` | 持久化根对象（Preferences 一个 key 存整份 JSON） |

### 2.2 状态变化

用户可见状态由三部分组成：**环境**（可随意改）、**设备**（被引擎或手动改）、**规则**（被编辑改）。
引擎执行是唯一同时改动「设备 + 规则（lastFiredAt）+ 日志（新增）」的操作：

```
用户操作                → 状态变化                          → 持久化动作
拖动环境滑块            → snapshot.env                        → Preferences（松手即存）
手点设备开关/档位       → snapshot.devices[i]                 → Preferences
编辑/启停/删除规则      → snapshot.rules                      → Preferences
执行一次联动/场景演练   → devices + rules.lastFiredAt + logs  → Preferences + RDB.insert(每条日志)
恢复出厂                → 全部回收种子值                      → 删除快照 key + 清空 trigger_log
```

### 2.3 模块间数据流

```
[EnvRow 滑块] --onValueChange(key,value)--> [Index.applyMetric]
      --> 新建 EnvState --> [Index.setEnv] --> cloneSnapshot() --> @State snapshot（界面刷新）
[执行按钮] --> [Index.execute] --> runEngine({rules,devices,env,now,source})
      --> EngineOutcome{devices,rules,logs,conflicts}  --> 回写 snapshot --> Preferences
      --> appendLogs(logs) --> [Repository.appendLogs] --> RDB --> queryLogs --> 日志 Tab
[RuleEditor] --保存--> validateRule() --> upsertRule() --> Repository.saveSnapshot --> router.back()
      --> [Index.onPageShow] --> reload() --> 界面与最新快照一致
```

### 2.4 一致性策略

- **单一数据源**：`Snapshot` 是唯一权威；Preferences 里存的就是它序列化后的 JSON。
- **不可变更新**：每次改动都通过 `cloneSnapshot()` 造新对象再赋值给 `@State`，
  避免 ArkUI 观察不到嵌套字段变化导致的「数据变了但界面不动」。
- **写后回读**：日志写入后重新 `queryLogs()`，保证界面显示的就是库里的内容。

## 3. 边界与异常分析

| 编号 | 场景 | 处理方式 | 验证用例 |
| --- | --- | --- | --- |
| E-1 | 快照 JSON 被截断/损坏 | `parseSnapshot` 捕获异常返回 `null`，上层回退种子数据并提示 | `codec.test.ts` 异常用例 |
| E-2 | 快照版本高于当前程序（降级安装） | 版本号 > `SNAPSHOT_VERSION` 直接拒绝解析，避免写坏新格式 | `codec.test.ts` 异常用例 |
| E-3 | 快照字段类型脏（`"hot"`、`level=260`、`power="yes"`） | 逐字段清洗：非数字回退默认值、数值裁剪到区间、非布尔回退 `false` | `codec.test.ts` 边界用例 |
| E-4 | 动作指向已删除/不存在的设备 | 跳过该动作并在日志标注「动作目标不存在」，其余动作照常执行 | `engine.test.ts` 异常用例 |
| E-5 | 环境数据为 `NaN` | `evaluateCondition` 判 `false`，不抛异常、不误触发 | `engine.test.ts` 异常用例 |
| E-6 | 动作 `level` 越界（-20 / 180） | 执行时裁剪到 `0..100`；表单侧直接校验拦截 | `engine.test.ts` 边界用例 |
| E-7 | 规则没有任何条件 | 语义定义为「永不触发」，避免空条件误开全场设备 | `engine.test.ts` 边界用例 |
| E-8 | 冷却期内的重复触发 | 跳过并计入 `skippedCount`，不写日志；冷却结束后恢复 | `engine.test.ts` 边界用例 |
| E-9 | 阈值恰好等于实测值 | `gte/lte/eq` 含等号命中，`gt/lt` 不含；`eq` 使用 1e-6 容差 | `engine.test.ts` 边界用例 |
| E-10 | 规则数量到 12 条上限 | `canAddRule` 拦截，界面提示先删除旧规则 | `validator.test.ts` 边界用例 |
| E-11 | 两条规则控制同一设备 | 高优先级胜出；同优先级按 ID 升序；生成 `ConflictNote` | `engine.test.ts` 冲突用例 |
| E-12 | Preferences/RDB 初始化失败 | `isStorageReady()` 为 false，界面顶部横幅提示「内存态」，功能仍可用 | 手动验证 |
| E-13 | 首次启动（无任何历史数据） | `loadSnapshot` 返回种子数据并立即写盘，保证第二次启动可恢复 | 手动验证 |

## 4. 模块划分与接口

### 4.1 模块

| 模块 | 文件 | 职责 | 输入 → 输出 |
| --- | --- | --- | --- |
| 表现层 | `pages/Index.ets` | 四 Tab 主界面，持有界面状态，串联所有交互 | 用户手势 → 状态更新 + 调用领域/数据层 |
| 表现层 | `pages/RuleEditor.ets` | 规则草稿编辑、校验提示、保存 | 路由参数 `ruleId` → 保存后的快照 |
| 组件层 | `components/*.ets` | 设备卡、环境行、规则卡、日志卡、场景卡 | `@Prop` 数据 + 回调事件 |
| 领域层 | `domain/DormLinkDomain.ts` | 模型定义、条件求值、引擎执行、冲突裁决、校验、编解码、种子数据 | 纯数据 → 纯数据（无副作用） |
| 数据访问层 | `service/DormLinkRepository.ets` | Preferences 快照读写、RDB 日志读写、异常降级 | 快照/日志 → 持久化结果 |
| 测试 | `tools/tests/*.test.ts`、`entry/src/test/*.test.ets` | 领域层自动化测试 | 用例 → 断言结果 |

### 4.2 领域层对外接口

| 接口 | 输入 | 返回 | 异常/边界 |
| --- | --- | --- | --- |
| `runEngine(input: EngineInput)` | `rules`、`devices`、`env`、`now`、`source` | `EngineOutcome`（设备、规则、日志、冲突、命中/跳过数） | 不修改入参；目标设备缺失、NaN 均安全跳过 |
| `evaluateCondition(cond, env)` | 条件 + 环境 | `boolean` | 非有限数返回 `false`；未知 op 返回 `false` |
| `evaluateRule(rule, env)` | 规则 + 环境 | `boolean` | 空条件返回 `false`；`and/or` 分别短路 |
| `isCoolingDown(rule, now)` | 规则 + 时间戳 | `boolean` | `cooldownSec<=0` 或 `lastFiredAt<=0` 返回 `false` |
| `sortCandidates(rules)` | 规则数组 | 新数组 | 优先级降序，同优先级按 ID 升序，稳定可复现 |
| `validateRule(rule, allRules, deviceIds, selfId)` | 草稿规则 + 上下文 | `ValidationResult{ok, issues[]}` | 一次返回全部问题，包含字段名与中文提示 |
| `dumpSnapshot(snapshot)` | 快照 | JSON 字符串 | 纯字符串化 |
| `parseSnapshot(text)` | 字符串 | `Snapshot \| null` | 空串/坏 JSON/非对象/版本过新 → `null` |
| `migrateSnapshot(text)` | 字符串 | `Snapshot \| null` | v1 缺字段按默认值补齐 |
| `cloneSnapshot(source, now)` | 快照 + 时间 | 新快照 | 深拷贝数组元素，保证不可变更新 |
| `upsertRule/removeRule/replaceDevice/findRule/findDevice` | 数组 + 目标 | 新数组或对象 | 未命中时返回原样/`null` |
| `seedRules/seedScenarios/defaultSnapshot/defaultDevices/defaultEnv` | 时间戳 | 种子数据 | 幂等 |

### 4.3 数据访问层接口

| 接口 | 输入 | 返回 | 异常处理 |
| --- | --- | --- | --- |
| `init(context)` | UIAbilityContext | `Promise<void>` | 分别 try/catch Preferences 与 RDB，记录 `lastError` |
| `loadSnapshot(now)` | 时间戳 | `Promise<Snapshot>` | 旧数据迁移失败/损坏 → 种子数据 |
| `saveSnapshot(snapshot)` | 快照 | `Promise<boolean>` | 失败返回 `false`，界面 Toast 提示 |
| `appendLogs(logs)` | 日志数组 | `Promise<number>`（写入条数） | 逐条插入，异常记录并继续 |
| `queryLogs(limit)` | 条数上限 | `Promise<LogEntry[]>` | 失败返回空数组 |
| `clearLogs()` / `clearSnapshot()` | — | `Promise<boolean>` | 失败返回 `false` |
| `resetAll(now)` | 时间戳 | `Promise<Snapshot>` | 清空后写回种子数据 |
| `isStorageReady()` / `getLastError()` | — | `boolean` / `string` | 供界面展示降级状态 |

## 6. 测试与验收

### 6.1 测试策略

- **领域层**：纯函数，用 Node 24 的 `node --test` 直接执行同一份 `.ts` 源码（无需编译），
  断言用 `node:assert`；覆盖正常、边界、异常三类。
- **UI 层**：DevEco 本地单测（Hypium）镜像同一批用例；界面行为通过真机/模拟器手动走查（见 6.4）。
- **持久化**：`codec.test.ts` 模拟「改环境 → 触发 → 保存 → 重启解析」全链路；
  真机层面通过「杀进程再启动」人工验证（见截图清单第 6 项）。

### 6.2 用例分布

| 类别 | 数量 | 代表用例 |
| --- | --- | --- |
| 正常 | 12 | 单/双条件命中、或逻辑、多规则不同设备、种子数据完整性、快照往返、重启恢复 |
| 边界 | 15 | `gte/gt` 等值、`eq` 容差、level 0/100/越界、冷却窗口、条件数 3/4、阈值端点、优先级 1/10/0/11、规则数 12、v1 迁移、脏字段清洗、200 次往返性能 |
| 异常 | 9 | 目标设备不存在、环境 NaN、零条件、空/坏 JSON、版本过新、空名/重名/超长、空动作、冷却越界 |

实测：**36/36 通过**（`node --test`，约 0.2s）。完整命令见 README 4.3。

### 6.3 验收方式

1. 打开 App，驾驶舱应显示 3 个环境滑块、4 台设备、6 条内置规则（5 条启用）。
2. 把温度拖到 28 以上并「执行一次联动」，风扇应开启且日志新增记录（含执行序号与条件文案）。
3. 到「场景」点「梅雨午后」一键演练，加湿器与窗帘应联动，结果卡提示冲突裁决（若存在）。
4. 规则 Tab 新建一条规则，故意留空名称或填 101 的湿度阈值，应提示具体错误并阻止保存。
5. 杀掉 App 后重新打开：环境值、设备状态、规则、日志应与关闭前一致。
6. `node --test tools/tests/*.test.ts` 应输出 36 条全部通过。

见 `docs/截图与录屏清单.md`，其中 6 个步骤即为验收演示路径。

## 7. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 引擎单次求值 12 条规则应在 10ms 内；快照 200 次序列化+反序列化 < 50ms（已测） |

| 隐私 | 全部数据留在本机，无网络请求、无权限申请 |
